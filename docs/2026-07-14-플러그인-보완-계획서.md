# TickTick Tag Progress 플러그인 보완 계획서

> [!summary] 계획 요약
> 이 계획서는 두 단계로 구성된다.
>
> - **1부 (지금 당장 · v0.2.0):** 현재 기능을 신뢰할 수 있게 만드는 안전 수정(P0)과, 새 데이터 없이 스냅샷만으로 완성되는 조망 기능 5개.
> - **2부 (1개월 후 · v0.3.0 후보):** 4주 사용 기록의 측정 트리거를 충족한 항목만 선별 구현하는 기능 5개.
>
> 원칙은 종합안 문서를 그대로 따른다 — **플러그인은 월간 조망·예외 발견·문맥 진입을 위한 얇은 관문이며, TickTick이 실행의 정본, MECH_WIKI가 판단과 지식의 정본이다.**

---

## 0. 계획의 전제

### 0.1 구현 순서 원칙

1. **신뢰가 조망보다 먼저다.** 날짜가 틀리고 완료 쓰기 결과가 불명확한 상태에서 조망 기능을 얹으면 잘못된 데이터를 더 잘 보이게 만들 뿐이다. 1부 Phase 1(안전 수정)을 전부 끝낸 뒤 Phase 2(조망 기능)를 시작한다.
2. **모든 항목은 회귀 테스트와 함께 머지한다.** 각 항목의 완료 조건에 테스트 목록을 명시했다. `npm run verify`(typecheck + vitest + build) 통과가 머지 조건이다.
3. **write 표면은 넓히지 않는다.** 이 계획서의 어떤 항목도 `POST …/complete` 외의 쓰기 endpoint를 추가하지 않는다. `endpoint-guard.ts`의 allow-list는 그대로 유지한다.
4. **1개월 후 항목은 전부 구현하는 목록이 아니다.** §2.0의 채택 조건을 충족한 항목만, 원칙적으로 한 번에 하나만 구현한다.

### 0.2 버전 계획

| 버전 | 범위 | 목표 시점 |
|---|---|---|
| v0.2.0 | 1부 전체 (Phase 1 + Phase 2) | 즉시 착수 |
| v0.3.0 | 2부 중 채택 조건을 충족한 항목 | 2026-08-11 Phase C 재평가 이후 |

# 1부. 지금 당장 보완 및 구현할 기능

## Phase 1 — 신뢰 회복 (안전 수정)

### 1-1. 로컬 날짜 정규화 (P0-1)

#### 역할 및 구현 이유

현재 `src/core/period.ts`의 `datePart()`는 ISO 문자열 앞 10자리를 그대로 날짜로 사용한다. TickTick API는 `2026-07-14T15:30:00.000+0000` 형태의 UTC 오프셋 표기를 반환하므로, KST 자정~08:59 사이의 일정은 하루 앞당겨 표시되고 월초 태스크는 이전 달로 빠진다. 2026-07 스냅샷 기준 저장된 날짜값 48개 중 5개에서 UTC 날짜와 Asia/Seoul 날짜가 실제로 달랐다. **가능성이 아니라 현재 데이터로 재현되는 결함이며, 월간 조망이라는 플러그인의 본래 목적을 직접 훼손하므로 가장 먼저 고친다.**

`normalizer.ts`는 이미 `timeZone`(35행)과 `isAllDay`(36행)를 보존하고 있으나 어떤 계산에도 사용되지 않는다. 재료는 다 있고 계산만 빠져 있는 상태다.

#### 구현 계획

**1단계 — 로컬 날짜 모듈 신설: `src/core/local-date.ts`**

```ts
export function toLocalDate(
  iso: string,
  timeZone: string | undefined,
  isAllDay: boolean,
  fallbackTimeZone: string, // Intl.DateTimeFormat().resolvedOptions().timeZone
): string; // 'YYYY-MM-DD'
```

- 구현은 `Intl.DateTimeFormat('en-CA', { timeZone, year: 'numeric', month: '2-digit', day: '2-digit' })`를 사용한다. 외부 라이브러리를 추가하지 않는다.
- 우선순위: 태스크의 `timeZone` → `fallbackTimeZone`(시스템 시간대). all-day 태스크는 TickTick이 태스크 시간대의 자정으로 저장하므로 같은 규칙으로 정확히 풀린다.
- 파싱 불가능한 문자열은 `null`을 반환하고 호출부가 "기간 미지정"으로 처리한다(fail-closed).

**2단계 — `NormalizedTask`에 파생 필드 추가**

- `contracts.ts`의 `NormalizedTask`에 `localStartDate?: string`, `localDueDate?: string` 추가.
- `normalizer.ts`의 `normalizeTask()`에서 **한 번만** 계산한다. 이후 집계·표시·오늘·지연 판단은 전부 이 두 필드만 사용한다(원시 ISO를 다시 자르는 코드를 전부 제거).
- `snapshot-store.ts`: `schemaVersion`을 2로 올린다. v1 스냅샷 로드 시 `sanitizeState()`에서 원시 `startAt`/`dueAt`/`timeZone`/`isAllDay`로 로컬 날짜를 재계산해 마이그레이션한다(스냅샷 폐기 없이 이전 데이터 유지).

**3단계 — 호출부 교체**

| 파일 | 변경 |
|---|---|
| `core/tag-progress-aggregator.ts` 25-27행 | `startAt ?? dueAt` → `localStartDate ?? localDueDate` |
| `core/sync-service.ts` 45-49행 | projectData 월 범위 필터를 로컬 날짜 기준으로 교체 |
| `main.ts` 118-122행 | `getDashboardModel`의 scheduled 판정 동일 교체 |
| `ui/dashboard-renderer.ts` 159행 | `task.dueAt?.slice(0, 10)` → `task.localDueDate` |

**4단계 — 회귀 테스트 (`tests/local-date.test.ts`, `tests/period.test.ts` 확장)**

- KST 자정 경계: `2026-07-14T15:00:00.000+0000` + `Asia/Seoul` → `2026-07-15`
- UTC 15:00 직전: `2026-07-14T14:59:59.000+0000` + `Asia/Seoul` → `2026-07-14`
- 월말→월초 경계: `2026-06-30T15:30:00.000+0000` + `Asia/Seoul` → `2026-07-01` (7월 스냅샷에 포함되어야 함)
- all-day + `timeZone` 존재/부재 각각
- `timeZone` 없는 태스크의 fallback 동작
- 파싱 불가 문자열 → null → 기간 미지정 처리

**완료 조건:** 위 테스트 전부 통과 + 기존 스냅샷(v1) 로드 시 데이터 손실 없이 마이그레이션됨을 테스트로 증명.

### 1-2. API 질의 창 ±1일 버퍼

#### 역할 및 구현 이유

날짜 결함은 표시 계층만의 문제가 아니다. `sync-service.ts:37`이 `getMonthRange()`의 순수 날짜 문자열을 그대로 `/task/filter`·`/task/completed`의 `startDate`/`endDate`로 보내는데, 서버가 이 경계를 어느 시간대로 해석하는지 보장이 없다. 1-1로 로컬 계산을 고쳐도 **월초·월말 태스크가 조회 자체에서 누락되면 스냅샷에 존재하지 않아 고칠 수 없다.** 질의는 넓게 받고 로컬에서 정확히 거르는 것이 안전하다.

#### 구현 계획

- `period.ts`에 `getQueryRange(month): { startDate; endDate }` 추가 — `getMonthRange()`의 앞뒤로 1일씩 확장한 범위를 반환.
- `sync-service.ts`의 두 API 호출만 `getQueryRange()`를 사용하도록 교체. 로컬 필터링(`clampTaskToMonth`)은 정확한 월 범위를 유지하므로 화면에는 영향이 없고, 경계 태스크의 누락만 사라진다.
- 테스트: 월 경계 태스크가 확장 질의로 들어와서 로컬 필터에 의해 정확히 포함/제외되는 시나리오.

**완료 조건:** 6월 30일 저녁(KST) 시작 태스크가 7월 조회에서 수집되고, 로컬 필터가 7월 1일로 정확히 배치.

### 1-3. `includeTags` × 미분류 행 충돌 수정

#### 역할 및 구현 이유

`main.ts:114-117`에서 포함 태그 필터가 집계 후 행 단위로 적용되는데, 미분류 행의 키는 include 목록에 존재할 수 없으므로 **포함 태그를 설정하는 순간 미분류 행이 영구히 사라진다.** 종합안 §4.1(포함 태그를 활성 프로젝트로 제한)과 §4.3(주간 점검 때 미분류 표시를 켠다)을 동시에 따르면 주간 점검이 무력화된다. 운영 계획 전체의 전제를 깨는 상호작용 버그이므로 P0급으로 처리한다.

부수 결함도 함께 수정한다: 실제 TickTick 태그 이름이 `미분류`인 경우 가상 미분류 행과 병합된다.

#### 구현 계획

- `tag-progress-aggregator.ts`: 가상 미분류 행의 키를 예약 키 `__untagged__`로 분리하고 `displayName`만 `미분류`로 유지. 실제 태그와의 충돌이 구조적으로 불가능해진다.
- `main.ts` 필터 로직 수정:

```ts
.filter((row) =>
  (row.tagKey === UNTAGGED_KEY
    ? this.settings.showUntagged
    : (include.size === 0 || include.has(row.tagKey)) && !exclude.has(row.tagKey)))
```

- 미분류 행은 include/exclude의 지배를 받지 않고 오직 `showUntagged` 토글만 따른다.
- 테스트: (a) includeTags 설정 + showUntagged=true → 미분류 행 표시, (b) showUntagged=false → 숨김, (c) 실제 태그 `미분류`는 별도 행으로 유지.

**완료 조건:** 종합안 §4.1 권장 설정 상태에서 주간 점검 루틴(미분류 켬)이 실제로 동작.

### 1-4. `SyncService` 월 키잉 + 불필요한 `getTags()` 제거

#### 역할 및 구현 이유

`sync-service.ts:27-31`의 in-flight dedupe는 `selectedMonth`를 비교하지 않는다. 7월 동기화가 진행 중일 때 8월 동기화를 요청하면 **7월 결과가 8월 요청의 결과로 반환된다.** 지금은 `main.ts`의 `syncing` 플래그가 우연히 막고 있지만, 1-5의 완료 흐름이 같은 인스턴스를 공유하므로 완료 write 안전화 이전에 반드시 제거해야 할 잠재 결함이다.

또한 `sync-service.ts:35`의 `getTags()` 호출은 결과가 버려진다. 매 동기화마다 API 호출 1회를 낭비하며 rate-limit 예산만 소모하므로 제거한다.

#### 구현 계획

- `inFlight: Promise | null` → `inFlight = new Map<string, Promise<SyncSnapshot>>()` (월 키). 같은 월 요청만 기존 promise를 재사용한다.
- `getTags()` 호출 제거. `coverage.successfulCalls`에서 `'tag'` 항목 제거. `SyncApi` 인터페이스에서 `getTags` 삭제(클라이언트의 메서드는 유지 — 2부 기능에서 태그 색상에 쓸 수 있으므로 API 표면만 남긴다).
- 테스트: 서로 다른 월의 동시 sync가 각자의 스냅샷을 반환, 같은 월 동시 요청은 단일 네트워크 호출.

**완료 조건:** 월 불일치 재사용이 테스트로 재현 불가능해짐.

### 1-5. 완료 쓰기 안전화 (P0-2)

#### 역할 및 구현 이유

현재 완료 흐름의 결함은 세 겹이다.

1. **오래된 스냅샷 기준 완료:** `main.ts:185-204`는 스냅샷 나이를 확인하지 않는다. 며칠 전 스냅샷의 태스크를 완료 대상으로 삼을 수 있고, 그 사이 TickTick에서 제목·상태·프로젝트가 바뀌었어도 모른다.
2. **완료 POST 자동 재시도:** `official-open-api-client.ts:86-104`의 `request()`가 읽기·쓰기 공용이라 완료 POST도 timeout·5xx에서 자동 재전송된다. timeout 후 재전송은 "이미 성공한 요청의 중복 전송"일 수 있다.
3. **결과 미확정의 거짓 보고:** timeout 시 `main.ts:222`가 "태스크는 변경되지 않았습니다"라고 단정하지만 실제로는 서버에서 완료됐을 수 있다.

완료는 이 플러그인의 유일한 외부 write이므로, 종합안이 요구하는 preview → 승인 → live 검증 계약을 코드로 강제한다. 이 항목이 끝나기 전까지는 종합안대로 **완료는 TickTick 원본에서만 수행하는 운영을 유지한다.**

#### 구현 계획

**1단계 — 쓰기 전용 요청 경로 분리 (`official-open-api-client.ts`)**

- `request()`에 내부 옵션 `{ retry: boolean }`을 추가하고 `completeTask()`는 `retry: false`로 호출한다. 쓰기 요청은 network·timeout·5xx 어떤 경우에도 자동 재전송하지 않는다.
- timeout 시 던지는 오류를 `TickTickHttpError(0, 'unknown-outcome')`으로 구분한다(신규 kind). Obsidian `requestUrl`은 요청 중단(abort)을 지원하지 않으므로, timeout 이후 늦게 도착하는 응답은 무시하고 **재전송하지 않는 것**으로 이중 전송을 방지한다.
- `errors.ts`: `kindForStatus()`에 404 → `'not-found'` 추가. 완료 대상이 삭제·이동된 경우(오래된 스냅샷에서 가장 흔한 실패)를 현재의 `'contract'` 오분류에서 분리해 "태스크가 삭제되었거나 이동되었습니다. 다시 동기화하세요."로 안내한다.

**2단계 — 완료 절차 재설계 (`task-completion-service.ts`)**

완료 절차를 다음 상태 기계로 재구현한다.

```
[진입 차단 게이트] → [live read 사전 검증] → [preview 재확인] → [POST(재시도 없음)]
     → 성공: [사후 exact read 검증] → [월 재동기화]
     → timeout: [결과 미확정 상태] → 사용자 조작으로 exact read → 상태에 따라 종료/재시도 허용
```

1. **진입 차단 게이트** (`main.ts`의 `requestTaskCompletion`): 다음 중 하나면 모달을 열지 않고 재동기화를 안내한다 — (a) `snapshot.generatedAt`이 TTL 초과(기본 30분, `settings.completionTtlMinutes`로 조정 가능), (b) `lastAttempt`가 스냅샷 이후의 실패, (c) coverage가 `complete`가 아님.
2. **live read 사전 검증**: 모달 확인 직전 `getTask(projectId, taskId)`를 호출해 ID·제목·프로젝트·상태를 스냅샷과 대조한다. `openTaskNote`(`main.ts:175`)가 이미 같은 패턴을 쓰므로 구현 비용이 낮다.
   - 상태가 `open`이 아니면: "이미 완료된 태스크입니다" 안내 후 중단, 재동기화 제안.
   - 제목·프로젝트가 스냅샷과 다르면: **기존 승인 폐기.** 모달을 live 값으로 갱신해 재승인을 요구한다.
3. **POST**: 재시도 없는 경로로 1회 전송.
4. **결과 미확정 처리**: `unknown-outcome`이면 모달을 닫지 않고 "결과 미확정 — TickTick 반영 여부를 확인해야 합니다" 상태로 전환, [상태 확인] 버튼이 exact read를 수행한다. 이미 완료됨 → 성공으로 종료. 여전히 open → 그때만 재시도 버튼 활성화. **exact read 없이는 재전송 불가를 코드로 강제한다.**
5. **사후 검증**: POST 성공 후에도 exact read로 `status === completed`를 확인한다. 불일치 시 성공 Notice 대신 경고를 표시한다.
6. `completeAndRefresh`의 "이미 open이 아니면 조용히 resolve"(`task-completion-service.ts:29`) 제거 — live read 도입으로 이 경로가 실제로 밟히게 되므로, 명시적 결과 타입 `{ outcome: 'completed' | 'already-completed' | 'unknown' }`을 반환하고 `main.ts`가 그에 맞는 Notice를 낸다.

**3단계 — 회귀 테스트 (`tests/task-completion-service.test.ts` 신설·확장)**

- TTL 초과 스냅샷 → 진입 차단
- live read에서 상태 completed → 중단 + already-completed 보고
- live read에서 제목 변경 → 재승인 요구
- timeout → unknown-outcome, exact read 전 재시도 불가
- unknown 후 exact read가 completed 반환 → 성공 종료 (재전송 0회 검증)
- POST 404 → not-found 안내
- 사후 검증 불일치 → 경고 경로
- **완료 POST가 어떤 실패 시나리오에서도 2회 이상 전송되지 않음** (transport 호출 횟수 검증)

**완료 조건:** 위 테스트 전부 통과. 이후 종합안 §8의 "완료 결과 미확정·stale write 시도 0건" 관찰을 시작하고, 0건이 확인될 때까지 대시보드 완료 버튼 사용을 재개하지 않는다.

### 1-6. 프로젝트·상태·coverage 정합성 (P0-3)

#### 역할 및 구현 이유

세 가지 정합성 결함을 하나의 묶음으로 수정한다.

1. **상태 충돌의 조용한 해소:** `sync-service.ts:50-52`에서 `filterTasks`와 `getCompletedTasks`가 같은 태스크를 다른 상태로 보고하면 먼저 들어온 쪽이 조용히 이긴다. 종합안 원칙(충돌은 추정하지 말고 exact read로 해소)에 위배된다.
2. **coverage 어휘의 공동화(空洞化):** `contracts.ts:76`에 `partial`/`unknown`이 정의돼 있으나 생성 경로가 없고, `snapshot-store.ts:62`는 `complete` 외를 거부한다. 비문서화 endpoint(`/task/filter`, `/task/completed`)가 언제든 사라질 수 있는 상황에서, 부분 실패를 표현할 수단이 없으면 전체 동기화가 all-or-nothing으로 깨진다.
3. **개인 vault 결합 하드코딩:** `project-mapper.ts:22-26`의 `UNIOS8K` 특례, `task-note-repository.ts:82`·`obsidian-task-note-port.ts:33`의 `40. Projects` 경로, `equivalentKeys()`의 U/UNI 접두사 자동 확장. 자동 확장은 다중 매치만 걸러내고 **단일 오탐은 통과시키는** 추정 매핑이라 fail-closed 원칙에 어긋난다.

#### 구현 계획

**1단계 — 상태 충돌 exact read 해소 (`sync-service.ts`)**

- `rawById` 병합 시 같은 id의 `status`가 소스 간 다르면 충돌 목록에 적재한다.
- 충돌 태스크는 `getTask()` exact read로 해소한다(월 25개 규모에서 충돌은 0~2건 수준이므로 호출 부담 없음).
- exact read 실패 시 해당 태스크의 상태를 `unknown`으로 저장하고 coverage에 기록한다. `unknown` 상태 태스크는 집계에서 제외하되 요약에 "상태 미확정 N건"으로 노출한다(1부 Phase 2의 요약 헤더와 연결).

**2단계 — coverage `partial` 실사용 + 성능 저하 경로 (`sync-service.ts`, `snapshot-store.ts`)**

- `Promise.all`을 `Promise.allSettled`로 전환한다. `/task/filter`·`/task/completed`가 실패해도 `project/{id}/data` 결과만으로 스냅샷을 구성하고 `coverage.status = 'partial'`, `failedCalls`에 사유를 기록한다. `getProjects` 또는 모든 projectData 실패 시에만 동기화 전체를 실패 처리한다.
- `snapshot-store.sanitizeCoverage`가 `partial`을 허용하도록 수정하되, **완료 write 게이트(1-5)는 `complete`만 통과**시킨다. 조회는 관대하게, 쓰기는 엄격하게.
- 대시보드 status 표기: 현재의 `'전체 조회'` 하드코딩(`dashboard-renderer.ts:53`)을 coverage 반영으로 교체 — `complete`/`partial`(경고색)/`상태 미확정 포함`.

**3단계 — 하드코딩 제거·설정화 (`settings-model.ts`, `project-mapper.ts`, 노트 계층)**

- 설정 추가: `projectsRootFolder`(기본 `40. Projects`), `taskNotesSubfolder`(기본 `TickTick Notes`). `task-note-repository.ts`·`obsidian-task-note-port.ts`의 경로 상수를 설정 참조로 교체.
- `project-mapper.ts`: `UNIOS8K` 특례 삭제. `equivalentKeys()`의 접두사 자동 확장 삭제. 매핑 근거는 **폴더명 정확 일치(정규화 후) + 명시적 `projectAliases`** 둘만 남긴다. 기존에 자동 확장으로 매핑되던 케이스는 설정의 alias로 이관하도록 릴리스 노트에 안내한다(예: `mpt → <해당 프로젝트 폴더명>`).
- 매핑 불가·다중 매치는 기존대로 예외/null(fail-closed)을 유지하고, 오류 메시지에 "설정 → 프로젝트 alias에 매핑을 추가하세요"를 포함한다.

**4단계 — UI·문구 정합 (`dashboard-renderer.ts`, `settings.ts`, `README.md`)**

- 열 제목 `진행률` → `태스크 완료율`. 종합안의 언어 규칙(완료율은 소진율이지 설계 진척률이 아니다)을 UI에 반영한다.
- 설정 상단 설명 `읽기 전용으로 사용합니다` → `조회 + 사용자 확인형 완료 쓰기(태스크 완료 1종)로 사용합니다`. 실제 동작과 문구를 일치시킨다.
- 포함 태그 placeholder `UNIOS8K, UNI610H` → 실제 TickTick 태그 표기 예시(`uos8k, u610h`)로 교체. include 매칭은 소문자 정규화 정확 일치임을 설명에 명시한다.

**5단계 — 회귀 테스트**

- 상태 충돌 → exact read 해소 / read 실패 → unknown 격리
- filter 실패 + projectData 성공 → partial 스냅샷 생성, write 게이트 차단
- alias 삭제 후 자동 확장 케이스가 매핑 실패(fail-closed)로 떨어짐
- 설정된 경로로 노트 생성

**완료 조건:** 플러그인 코드에서 특정 프로젝트명·vault 경로 문자열이 사라지고, coverage 세 상태가 모두 실제 생성 가능해짐.

### 1-7. 월 요약 헤더 (Portfolio Summary Strip)

#### 역할 및 구현 이유

현재 대시보드는 태그 행부터 시작해 "이번 달 전체가 어떤 상태인가"를 답하는 요소가 없다. 요약 한 줄이 플러그인의 본래 목적(월간 조망)의 첫 화면이 된다:

```
활성 프로젝트 6 · 태스크 25 (완료 11) · 미분류 3 · 기간 미지정 4 · 상태 미확정 0 · 데이터 5시간 전
```

특히 **"데이터 N시간 전" freshness 표시는 1-5의 TTL 개념을 UI로 드러내는 장치**다. 오래된 스냅샷을 "전체 조회"로 믿는 현재 문제를 해소하고, 미분류·기간 미지정 개수를 상시 노출해 미분류 행을 평소 숨겨도(§4.1 운영) 예외의 존재 자체는 놓치지 않게 한다.

#### 구현 계획

- `DashboardModel`에 `summary` 필드 추가: `{ projectTagCount, taskTotal, taskCompleted, untaggedCount, unscheduledCount, unknownStatusCount, snapshotAgeMs }`. 계산은 `getDashboardModel()`에서 aggregation 결과와 `snapshot.generatedAt`으로 수행 — 신규 저장소 없음.
- `dashboard-renderer.ts`에 `renderSummary()` 추가(툴바 바로 아래). freshness 표기 규칙: 1시간 미만 `방금 전`/`N분 전`, 이후 `N시간 전`, 24시간 이상은 날짜. **TTL(1-5의 `completionTtlMinutes`) 초과 시 경고색 + "동기화 필요" 배지**로 완료 게이트와 시각적으로 연동한다.
- 미분류·기간 미지정 카운트는 include 필터 적용 **이전의** 전체 집계에서 계산한다(필터로 숨겨진 예외도 세어야 하므로).
- 테스트: 요약 수치가 스냅샷 fixture와 일치, TTL 경계에서 배지 전환. 기존 `tests/dashboard-renderer.test.ts` 확장.

**완료 조건:** 필터·토글 상태와 무관하게 예외 총량이 항상 보임.

### 1-8. `includeTags` 순서 기반 정렬 + 기타 구획

#### 역할 및 구현 이유

현재 정렬은 단순 가나다순(`aggregator.ts:72`)이다. 포트폴리오 조망에서는 사용자가 정한 우선순위가 화면 순서가 되어야 한다. 설정 UI 변경 없이 기존 `includeTags` 배열의 **순서**를 존중하는 것만으로 구현된다.

#### 구현 계획

- `main.ts`의 `getDashboardModel()`에서 행 정렬을 교체: include 목록에 있는 태그는 목록 내 순서대로, 목록 밖 태그(include가 비어 있을 때)는 가나다순, 미분류 행은 항상 마지막.
- include가 비어 있지 않은데 표시 대상인 행(미분류)은 "기타" 시각 구획으로 분리 — `dashboard-renderer.ts`에 얇은 구분선 한 줄.
- 설정 화면의 포함 태그 설명에 "입력 순서가 대시보드 표시 순서가 됩니다"를 추가.
- 테스트: 순서 보존, 미분류 최하단 고정.

**완료 조건:** `uos8k, u610h, u650a, u4100, shm-9g, mpt` 입력 시 그 순서 그대로 표시.

### 1-9. 태그 행 → Hub 열기 링크

#### 역할 및 구현 이유

종합안 §6이 P0 이후 1순위로 지정한 기능. 플러그인의 세 번째 목적(문맥 진입)을 완성하는 최소 단위다 — 태그 행에서 해당 프로젝트 Hub로 한 번에 이동한다. Handoff Card(2부 2-2)의 1차 단계이기도 하다.

#### 구현 계획

- **Hub 탐색 규칙:** `metadataCache`에서 frontmatter `type`이 Hub 타입(설정 `hubNoteType`, 기본 `project-hub`)이고 `project` 필드가 태그의 canonical 프로젝트와 일치하는 노트를 찾는다. canonical 해석은 1-6에서 정비한 `resolveCanonicalProject`(폴더 일치 + 명시 alias)를 재사용한다 — **같은 resolver를 태그 행과 task-note 목적지에 함께 쓴다**는 종합안 P0-3 원칙 그대로.
- **fail-closed:** 유일 매치일 때만 행에 Hub 아이콘 버튼을 표시한다. 0건·다중 매치는 버튼을 숨긴다(추정 이동 금지). 미분류 행에는 표시하지 않는다.
- `DashboardActions`에 `onOpenHub(tagKey)` 추가, `main.ts`에 `openProjectHub()` 구현(`openProjectsBase`와 동일한 TFile → openFile 패턴).
- Hub 매핑 계산은 렌더 시마다 vault 전수 탐색하지 않도록 `getDashboardModel()`에서 1회 수행해 모델에 포함한다.
- 테스트: 유일 매치 → 버튼 표시, 다중/무매치 → 숨김 (resolver 단위 테스트로 검증).

**완료 조건:** 활성 프로젝트 6개 태그 행에서 클릭 한 번으로 각 Hub 열림. 매핑 실패는 조용히 버튼 부재로 표현.

### 1-10. 정체 신호 — 마지막 완료 경과 표시

#### 역할 및 구현 이유

완료율은 같은 40%라도 "어제 완료가 있었던 40%"와 "20일째 멈춘 40%"를 구분하지 못한다. 전체 프로젝트 진행상황 파악에서 가장 유용한 단일 신호는 **"이 프로젝트에서 마지막으로 무언가 완료된 게 언제인가"**다. `completedAt`은 이미 스냅샷에 저장되고 있어(`contracts.ts:70`) 계산만 추가하면 된다. 종합안이 금지한 합성 건강 점수가 아니라 원인이 그대로 보이는 원시 신호이므로 §7 원칙과 충돌하지 않는다.

#### 구현 계획

- `TagProgress`에 `lastCompletedAt?: string` 추가. `aggregator`에서 해당 태그 태스크들의 `completedAt` 최댓값(기간 미지정 완료 포함)으로 계산.
- 렌더러: 진행률 셀 아래 보조 텍스트 `마지막 완료 N일 전`. 경과 계산은 1-1의 로컬 날짜 기준. 완료가 하나도 없으면 `이번 달 완료 없음`. **7일 이상 경과 시에만** 강조색 적용(임계값 상수, 설정화하지 않음 — 설정 표면 최소 유지).
- 테스트: 최댓값 선택, 완료 없음 표기, 임계값 강조.

**완료 조건:** 완료율이 같은 두 프로젝트의 정체 여부가 화면에서 구분됨.

### 1-11. 드릴다운 마감일 정렬 + 지연 배지

#### 역할 및 구현 이유

현재 드릴다운(`dashboard-renderer.ts:129-166`)은 스냅샷 순서 그대로 나열한다. 태그를 열었을 때 "가장 급한 것"이 위에 오고, 마감이 지난 미완료가 표시되어야 예외 발견이라는 목적에 부합한다. 종합안 §7이 보류한 것은 TickTick Today와 중복되는 **별도의 실행 큐(strip)**이고, 이미 연 태그 목록 안의 정렬·배지는 조망 기능이므로 성격이 다르다. 단, 지연 판정은 1-1의 로컬 날짜가 전제다.

#### 구현 계획

- 드릴다운 태스크 정렬: `localDueDate` 오름차순 → 미지정은 마지막 → 동일 날짜는 open 우선.
- 지연 판정: `status === 'open' && localDueDate < today`(오늘은 시스템 시간대의 로컬 날짜). 해당 태스크에 소형 `지연` 배지 + 날짜를 경고색으로.
- 테스트: 정렬 순서, 오늘 마감은 지연 아님, 시간대 경계에서 1-1 함수와 일관성.

**완료 조건:** 드릴다운을 열면 지연 태스크가 최상단에 배지와 함께 보임.

# 2부. 1개월 후 업데이트할 기능

## 2-0. 채택 원칙

2부 항목은 **전부 구현하는 목록이 아니다.** 종합안 §8의 주간 관찰 기록에서 아래 채택 조건을 충족한 항목만, 2026-08-11 Phase C 재평가에서 원칙적으로 **하나만** 고른다. 반복된 불편이 없으면 아무것도 추가하지 않는 것도 성공이다.

| 항목 | 채택 조건 (4주 관찰 트리거) |
|---|---|
| 2-1 이월 감지 | "이거 지난달에도 있었는데"라는 경험이 주간 기록에 2회 이상 |

### 2-1. 이월(carry-over) 태스크 감지 — 권장 1순위

#### 역할 및 구현 이유

`snapshot-store`는 월별 스냅샷을 이미 모두 보관한다(`state.snapshots[month]`). 같은 태스크가 여러 달 연속 미완료(open)로 등장하면 그것이 곧 backlog 부패의 신호다. 월간 완료율은 "이번 달에 무엇을 했나"만 보여주지만, 이월 감지는 "무엇이 계속 안 움직이는가"를 보여준다 — **전체 프로젝트 진행상황 파악이라는 특화 목적에 가장 직접적으로 기여하는 기능**이다. 새 스키마·새 API 없이 저장된 데이터의 교차 조회만으로 구현된다.

#### 구현 계획

**1단계 — 조회 함수 (`snapshot-store.ts`)**

```ts
getCarryOverMonths(taskId: string, beforeMonth: string, lookback = 3): number
// beforeMonth 이전의 연속된 스냅샷들에서 해당 id가 open으로 존재한 개월 수
```

- **관찰 불가 처리:** 스냅샷이 없는 달은 카운트를 중단한다(없는 데이터를 추정하지 않음 — fail-closed). "3개월째"는 "연속 3개 스냅샷에서 관찰됨"만을 의미하도록 툴팁에 명시한다.
- lookback 상한(기본 3, 최대 6)으로 계산량을 고정한다.

**2단계 — 표시**

- 드릴다운 태스크에 `N개월째 이월` 배지(2개월 이상부터). 1-11의 지연 배지와 나란히 표시하되 색을 구분한다.
- 요약 헤더(1-7)에 `이월 N건` 카운트 추가.
- 태그 행에는 표시하지 않는다(행 밀도 유지 — 예외는 요약과 드릴다운에서만).

**3단계 — 스냅샷 보존 정책 (동반 작업)**

- 이월 감지가 과거 스냅샷에 의존하게 되므로, 무기한 축적 문제를 함께 해결한다: `snapshot-store`에 보존 개월 수(기본 13개월) 초과 스냅샷 자동 정리(prune)를 추가한다. `exportState()` 시점에 수행해 `data.json` 성장을 차단한다.

**4단계 — 테스트**

- 연속 open 3개월 → 3, 중간 완료 → 리셋, 중간 스냅샷 부재 → 중단
- prune 후에도 lookback 범위 내 계산 정상
- 13개월 초과 스냅샷 제거 확인

**완료 조건:** 드릴다운에서 2개월 이상 이월 태스크가 즉시 식별되고, `data.json` 크기가 보존 정책으로 상한을 가짐.

### 2-2. Project Handoff Card

#### 역할 및 구현 이유

종합안 §6의 조건부 후보. Hub 링크(1-9)만으로 프로젝트 복원(중단했던 프로젝트의 맥락을 다시 잡는 것)이 2분을 넘는 사례가 반복될 때만, 링크를 세 줄 카드로 확장한다:

```
UNI610H · Stage 07 · health: active
현재 초점: 판금 탭 인서트 보완·BOM 삭제 누락 대응
대기: UNIOS8K 설계 완료 후 MAIN FRAME 보완
[Hub 열기] [최근 Daily] [관련 Case]
```

플러그인 안에 Hub 정보를 **복제하지 않고**(종합안 §4.3 금지 사항), Hub frontmatter를 읽기 전용으로 투영만 한다.

#### 구현 계획

- **데이터 소스:** 1-9에서 확정한 Hub 노트의 frontmatter에서 `stage`, `currentFocus`, `health`, `waitingFor`만 읽는다. `metadataCache` 조회만 사용(파일 read 없음), 렌더 시 캐시.
- **fail-closed 표시:** 필드가 없으면 해당 줄을 생략한다. 네 필드 모두 없으면 카드 대신 기존 Hub 링크만 남긴다. Hub 스키마를 플러그인이 요구·검증하지 않는다(정본은 Hub).
- **위치:** 드릴다운 패널 상단(태그를 열었을 때만 — 평상시 행 밀도 불변).
- **링크 3종:** Hub 열기(1-9 재사용), 최근 Daily(설정 `dailyFolder`의 최신 파일명 규칙 매치, 실패 시 버튼 숨김), 관련 Case(Bases 열기 재사용 + 태그 필터 안내).
- **하지 않는 것:** `waitingFor`의 age·SLA 계산(종합안 §7 보류 그대로 — 신뢰할 날짜 스키마가 없다), Hub 필드의 편집.
- 테스트: 필드 부분 존재 시 생략 렌더, 전무 시 카드 미표시, Daily 매치 실패 시 버튼 숨김.

**완료 조건:** 카드 도입 후 프로젝트 복원 2분 초과 사례가 관찰 기록에서 소멸.

### 2-3. 전월 대비 요약 한 줄

#### 역할 및 구현 이유

월말 회고 때 "지난달과 비교해 어땠나"를 요약 헤더에 텍스트 한 줄로 제공한다: `완료 14 → 11 · 이월 +3`. 전월 스냅샷이 이미 저장되어 있으므로 계산은 무료다. 단, 종합안이 경고한 "완료율의 성과 지표화" 함정에 가장 가까운 기능이므로 **숫자 비교 텍스트까지만 구현하고 그래프·추세선·점수화는 하지 않는다.**

#### 구현 계획

- `getDashboardModel()`에서 전월 스냅샷 존재 시 `summary.previousMonth = { taskCompleted, carryOverDelta }` 계산. 없으면 필드 생략(표시 안 함).
- 요약 헤더(1-7) 끝에 소형 텍스트로 렌더. 색상·아이콘 강조 없음(중립 표기 — 증감은 좋고 나쁨이 아니다).
- 테스트: 전월 부재 시 미표시, 수치 일치.

**완료 조건:** 회고 시 전월 스냅샷을 수동으로 여는 행동이 사라짐.

### 2-4. 주간 점검 모드

#### 역할 및 구현 이유

종합안 §4.3의 주간 루틴(미분류 켬 → 태그 오류·기간 미지정·이월 확인 → 미분류 끔)은 현재 설정 토글을 수동으로 왕복해야 한다. "점검 모드" 토글 하나로 이 루틴을 클릭 한 번으로 만든다. 루틴 자체가 정착하지 않았다면 기능을 만들어도 쓰지 않으므로, 4주 연속 수행 기록을 채택 조건으로 둔다.

#### 구현 계획

- `GanttDashboardView`에 뷰 상태 `reviewMode: boolean` 추가(툴바 토글 버튼). **설정을 변경하지 않는다** — 뷰의 일시 상태로만 동작하고 닫으면 원상복귀. 이것이 설정 왕복 방식과의 결정적 차이다.
- 점검 모드 활성 시: (a) include 필터 해제(전 태그 표시), (b) 미분류 행 강제 표시, (c) 기간 미지정·지연(1-11)·이월(2-1 도입 시) 태스크만 드릴다운에 필터, (d) 요약 헤더에 `점검 모드` 배지.
- 점검 항목 체크리스트는 만들지 않는다(새 정본 금지 — 기록은 기존 주간 리뷰 노트에 남긴다).
- 테스트: 모드 진입/이탈 시 설정 객체 불변, 필터 동작.

**완료 조건:** 주간 점검 소요가 설정 왕복 없이 화면 내에서 완결.

### 2-5. task-note metadata-only reconciliation

#### 역할 및 구현 이유

종합안 §6의 두 번째 조건부 후보. 태스크 노트의 `ticktickStatus` 등 관리 frontmatter가 실제 TickTick 상태와 달라 혼란을 준 사례가 반복될 때만 도입한다. **기존 exact-ID 노트의 관리 frontmatter만 갱신하며, 새 노트를 일괄 생성하지 않고 사용자 메모 본문(`## 작업 메모` 이하)은 절대 다시 쓰지 않는다.**

#### 구현 계획

- 새 명령 `TickTick 노트 메타데이터 일괄 갱신`:
  1. `listTaskNotes()`로 exact-ID 노트 수집(기존 포트 재사용).
  2. 각 ID를 현재 월 스냅샷과 대조, 스냅샷에 없는 ID는 `getTask()` exact read(노트 수만큼의 read — 실행 전 개수를 안내).
  3. **dry-run 미리보기 모달:** 변경될 노트 목록과 필드 diff(예: `ticktickStatus: open → completed`)를 보여주고 사용자 승인 후에만 실행. 승인 없는 자동 실행 경로는 만들지 않는다.
  4. 실행은 기존 `updateManagedFrontmatter`(`task-note-format.ts:89`)와 `processFrontMatter`만 사용 — 본문 불변이 구조적으로 보장된다. 관리 블록(`ticktick-managed`) 본문 갱신은 이 명령의 범위에서 제외한다(frontmatter만).
  5. TickTick에서 삭제된 태스크(404)의 노트는 수정하지 않고 결과 보고에 `원본 삭제됨 N건`으로만 표시한다(노트 삭제·이동은 사용자 몫).
- 테스트: 본문 바이트 불변 검증, 404 노트 무변경, dry-run과 실제 실행의 diff 일치.

**완료 조건:** stale 노트로 인한 혼란 사례가 관찰 기록에서 소멸. 자동 스케줄 실행은 도입하지 않는다.
